# Action Core — первая рабочая версия

> **Статус:** реализация V1 продолжается (2026-11-04). **Формат YAML, Registry/API и ручной ActionRun → Broker → настоящий Feedbrain → StepRun/ActionResult проверены на Windows Docker/PostgreSQL через Fortis Repo. код Action Scheduler, API и миграция `0006` добавлены; **запуск по расписанию на настоящем PostgreSQL/Docker ещё не проверен**. Внешние failed/timeout и restart также требуют проверки.** Прогресс и история — в [PROJECT.md](PROJECT.md); общие принципы — в [ARCHITECTURE.md](ARCHITECTURE.md); сетевые ограничения — в [SECURITY.md](SECURITY.md).
>
> **Цель V1:** создать Action с понятной инструкцией и простым Workflow → выполнить его через Broker и **реальный Feedbrain API** → увидеть результат/историю → настроить и проверить автоматический повторный запуск. AI должен иметь возможность **читать и запускать** Actions через доступный ему Fortis Repo, но вызов модели внутри Workflow для V1 не требуется.

## 1. Суть системы

**Action** — сохраняемое, прежде всего понятное человеку и AI описание работы. **Workflow** — необязательное, но машинно интерпретируемое описание операций. **Broker** проверяет указанные в шаге `tool` и `capability`, затем вызывает зарегистрированный адаптер инструмента. **Executor/Worker** организует выполнение и учёт результатов. **Scheduler** определяет время запуска.

Инструменты остаются **чёрными ящиками**. Наша система не реализует их бизнес-логику, а использует внешний контракт (REST, MCP, CLI или иной доступный интерфейс). В V1 рабочий инструмент только один — **Feedbrain**. Имя инструмента, операция и ссылка на источник явно указываются **в Action Workflow**, но URL, сетевые параметры и секреты доступа остаются в доверенной конфигурации адаптера. Action Core не зависит от Feedbrain.

В будущем можно подключать сторонние и собственные сервисы, программные процессы и AI как инструменты/исполнителей, создавать смешанные сценарии и добавлять накопительные представления. **Не проектируем реализацию этих расширений в V1**: первый тест должен доказать базовую цепочку и заменяемость слоя инструментов на уровне контрактов.

### Разделение ответственности

| Компонент | В V1 отвечает за |
|---|---|
| **Action Registry** | CRUD Action, версии текста/Workflow, выдача определения по API |
| **Workflow parser/validator** | Читает ограниченный YAML и проверяет схему, шаги, аргументы |
| **Broker** | Находит адаптер по `tool`, проверяет поддержку `capability` и передаёт `with`; адаптер проверяет параметры и результат |
| **Feedbrain adapter** | Вызывает существующий Feedbrain HTTP API и преобразует ответ в результат шага |
| **Execution worker** | Берёт ActionRun из очереди, выполняет шаги, записывает ход и статус |
| **Action scheduler** | По расписанию ставит ActionRun в очередь; не запускает AI и не заменяет RSS scheduler Feedbrain |
| **Run history** | Хранит привязку к ActionVersion, время, статус, вызванный инструмент и результат |

Это логические компоненты: в V1 допустимо использовать существующие FastAPI, PostgreSQL и Docker worker **без новых микросервисов**. Логика Action Core не должна напрямую читать Feedbrain `Resource`/`Subscription` таблицы или вызывать методы ingestion — только контракт адаптера.

## 2. Простой Workflow-язык

**Решение для V1:** небольшой строго валидируемый **YAML-формат**, а не новая текстовая грамматика. Как в Compose, человек читает конфигурацию, но это **не** Docker Compose specification. **Контракт закреплён валидатором** `src/info_hub/action_workflow.py` и тестами `tests/test_action_workflow.py`. Синтаксис соответствует проверяемой схеме; реальный запуск ActionRun подтверждён на развёрнутой PostgreSQL.

```yaml
name: Обновить архив AI-публикаций

instruction: |
  Синхронизируй выбранный источник и сохрани новые
  публикации для последующих исследований.

workflow:
  schema: 1
  steps:
    - id: refresh_feed
      tool: feedbrain
      capability: information.sync
      with:
        source:
          type: subscription
          id: 1

schedule:
  every_minutes: 60
```

**Как это интерпретируется:** `tool: feedbrain` — явный выбор инструмента, `capability: information.sync` — операция, `with.source` — структурированная ссылка на ресурс **этого инструмента**. В примере Feedbrain понимает `{type: subscription, id: 1}`. **Это не часть общего словаря Action Core:** другой адаптер может понимать `{type: file, id: "report.csv"}`, `{type: collection, name: "articles"}` и т. п. Общий валидатор разрешает JSON-подобные параметры, а конкретный адаптер проверяет поддерживаемые типы и значения. Пример с ID 1 требует реально существующей подписки; никакого универсального «источника №1» нет. URL/ключи доступа к инструменту остаются вне Action; `schedule` не является командой Feedbrain.

**Границы грамматики V1:**
- `name` и `instruction` — человеческое описание; Workflow необязателен для **хранения** Action.
- `workflow.schema` — номер версии нашей схемы, `steps` — упорядоченный список шагов; `id`, **`tool`**, `capability` и необязательный `with` — поля шага. Порядок последовательный.
- `schedule.every_minutes` в YAML — **предлагаемый интервал**, но не команда включения. Реальное расписание хранится отдельно в `ActionSchedule` и меняется через `PUT /actions/{id}/schedule`. Изменение расписания не создаёт новую версию Action. Без явного `enabled: true` автоматического запуска нет.
- В V1 достаточно **одной реально выполняемой capability**: `information.sync`. Новые capabilities регистрируем только вместе с проверяемым адаптером и контрактом.
- Workflow без поддерживаемого Broker/adapter можно сохранить как черновик, но **нельзя запускать как будто он исполним**. Запуск Action, содержащего только свободную инструкцию без Workflow, тоже не становится автоматически исполнимым без отдельного AI executor.
- Нет произвольного кода/`eval`, shell-команд, Python, HTTP URL из YAML, шаблонизации, циклов, условий, вложенных Actions, запуска моделей или маршрутизации через LLM. Не делаем вид, что умеем их обрабатывать.

**Реализация и проверка формата (готово):**
- `parse_action_yaml` использует PyYAML SafeLoader, запрещает YAML aliases, дублирование ключей, несколько документов и небезопасные YAML-типы. Максимальный документ — 64 000 символов.
- `validate_action_document` проверяет обязательные `name` и `instruction`, необязательные `workflow`/`schedule`, `workflow.schema: 1`, уникальные идентификаторы шагов, корректность параметров и ограничение в 24 шага.
- Общий YAML-валидатор **не знает** названий ресурсных типов Feedbrain. Для `feedbrain + information.sync` адаптер требует `with.source.type: subscription` и положительный целый `with.source.id`. Другие инструменты могут иметь иные параметры. Неизвестные инструменты/capabilities можно сохранить в Action, но нельзя исполнить без подходящего адаптера. Action без Workflow тоже нельзя запустить программным worker.
- Для расписания в V1 валиден только целочисленный `every_minutes` от 1 до 10 080 (одна минута — неделя). **Scheduler реализован в коде**, но ещё не проверен на обновлённом Windows Docker.
- Пример для будущих запусков: [examples/actions/rss_sync.yaml](../examples/actions/rss_sync.yaml). Проверить локально после установки зависимостей: `python -m info_hub.action_workflow examples/actions/rss_sync.yaml`. Команда **только валидирует и выводит нормализованное описание**, ничего не запускает.

**Почему не готовый workflow DSL целиком:** [Docker Compose](https://docs.docker.com/reference/compose-file/) описывает контейнерные сервисы; [GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) привязан к jobs/runners, а [CNCF Serverless Workflow](https://www.cncf.io/projects/serverless-workflow/) включает гораздо больше средств, чем требуется первому сценарию. Можно позднее перейти на готовый стандарт или использовать готовый движок, если реальная сложность оправдает миграцию. В V1 используем **обычный YAML parser + маленькую проверяемую схему**, а не собственный парсер языка.

## 3. Первая интеграция: Feedbrain

**Фактически существующий контракт Feedbrain** (см. [RSS-FIRST-SLICE.md](RSS-FIRST-SLICE.md)):

1. `POST /subscriptions/{subscription_id}/sync` — **HTTP 202** и `IngestionRun` (queued/running/completed/failed), а не готовый синхронный результат.
2. `GET /runs/{run_id}` — статус, счётчики `items_seen`/`items_created`/`items_updated`, ошибка.
3. `GET /sources` и `GET /subscriptions` — чтение существующей конфигурации; Feedbrain сам управляет RSS/Atom и фоновым polling.

**Broker/adapter должен:**
- по явному `tool: feedbrain` выбрать зарегистрированный адаптер, проверить `information.sync` и принять `with.source: {type: subscription, id: 1}`; преобразовать ID в путь Feedbrain API только внутри адаптера;
- получить идентификатор `IngestionRun` из ответа `202`, **дождаться конечного статуса** отдельными проверками `GET /runs/{id}` с ограничением по времени;
- вернуть общую структуру: `status`, `tool`, `external_run_ref`, счётчики/ссылка на результат; сообщить об ошибке или тайм-ауте, а не считать `202` успешным завершением;
- записать, какой инструмент фактически выполнил операцию, и его идентификаторы. Не передавать в контекст AI все RSS-публикации без запроса.

**Что реализовано и проверено в Broker:**

- `src/info_hub/action_broker.py`: `CapabilityBroker.dispatch_step` проверяет Workflow V1, находит адаптер по явному `tool`, проверяет его `capability` и возвращает `StepOutcome`. Два инструмента могут поддерживать одну capability, но выбор всегда явный. Неподдерживаемые инструмент/операция/параметры отклоняются **до** внешнего вызова.
- `src/info_hub/feedbrain_adapter.py`: `FeedbrainSyncAdapter` поддерживает только `information.sync`, вызывает по HTTP `POST /subscriptions/{id}/sync`, читает `GET /runs/{id}` до `completed`/`failed` или deadline. В результате возвращает `feedbrain:ingestion_run:{id}`, фактические счётчики и логический источник; ошибки и тайм-аут несут ссылку на внешний запуск, если она известна. Полученный статус `202` сам по себе **не считается успехом**.
- URL API и секреты остаются в **доверенной конфигурации адаптера**; выбор инструмента и ссылка на источник — **в YAML Action**. Клиент не следует HTTP redirects и не использует системные HTTP proxy. Никакого implicit fallback на другой инструмент/источник нет. Feedbrain может вернуть существующий активный `IngestionRun`, поэтому не утверждаем, что каждое выполнение создаёт новый внешний запуск.
- `src/info_hub/settings.py` и `compose.yaml` передают только `ACTION_FEEDBRAIN_URL` (по умолчанию `http://api:8000`). Привязок `ACTION_FEEDBRAIN_SOURCES_JSON` больше нет; `source` указан в Action. Подписку нужно выбрать из `GET /subscriptions`, а не угадывать её ID.
- `configured_broker()` собирает зарегистрированные адаптеры, а `ActionRun` API и отдельный worker вызывают Broker. **Этот путь проверен на Windows Docker (ActionRun #1);** сохранение YAML само по себе ничего не запускает.
- `tests/test_action_broker.py` проверяет реальный HTTP обмен с **локальным тестовым сервером**, успешные/ошибочные ответы, ожидание run, тайм-ауты, отказы при неверных идентификаторах и источниках, недопустимый URL из Action. **Дополнительно подтверждён реальный Feedbrain IngestionRun #6 через Broker;** негативные сценарии пока проверены только локальными тестами.

**Совместимость версий:** ранее сохранённые ActionVersion с `with.source: ai_articles` и без `tool` остаются доступными для чтения, но **не исполняются в новом формате**. Нужно опубликовать новую версию (например, v3) с явным инструментом и структурированным `source`; старые версии сохраняются неизменными.

**Критическая граница исполнения:** адаптер ожидает завершения удалённого `IngestionRun`. Его нельзя запускать **в том же единственном блокирующемся цикле worker**, который должен обработать очередь `IngestionRun`: получится ожидание самого себя и тайм-аут. Для V1 нужен **отдельный Action worker/процесс** (можно из общего Docker-образа) или доказанно неблокирующая конкурентная обработка; не требуется новый микросервис с отдельной БД.

**Важная ловушка проверки:** Feedbrain **уже сам** планирует RSS polling. Запуск Action по расписанию не должен неконтролируемо дублировать тот же сбор: для end-to-end выбрать тестовую подписку с большим штатным интервалом, а Action запускать отдельно, либо явно проверить взаимодействие двух планировщиков. Feedbrain может вернуть уже активный IngestionRun — это нужно учесть в истории, не создавать ложный «новый» результат.

Новый Tool/Adapter в будущем заменяет Feedbrain только при совпадении семантики и типов входа/выхода. `information.sync` **не** означает «любая операция любого API», а переносимость нельзя считать доказанной одним Feedbrain.

## 4. Сохранение, исполнение, история, расписания

### Минимальная модель V1

| Сущность | Нужные свойства |
|---|---|
| `Action` | ID, имя, текущая версия, признаки включения/удаления |
| `ActionVersion` | Номер, неизменяемый текст инструкции, проверенный/сохранённый Workflow; дата создания |
| `ActionSchedule` | Action, интервал, enabled, next_run_at/last_triggered_at; машиночитаемая политика |
| `ActionRun` | ID, ссылка на точную версию, инициатор (`manual`/`api`/`schedule`), статус, время запуска/завершения, ошибка |
| `StepRun / Event` | Step ID, capability, фактический tool, входные параметры или ссылки, внешний run id, статус и время |
| `ActionResult` | Сводка, статус, структурированный результат/ссылка; не полная копия архива |

Минимальные состояния Run: `queued → running → completed/failed`. Неизменяемость ActionVersion обязательна; при изменении инструкции/Workflow создаём новую версию. Изменение расписания не должно переписывать историю ActionVersion. После запуска Run должен быть закреплён за **конкретной** версией; изменение текущей версии не влияет на выполняющийся Run.

**Исполнение:** API создаёт Run в БД, worker забирает его и вызывает адаптер. API не ждёт окончания RSS fetch в одном HTTP-запросе. Scheduler встроен в отдельный `action-worker` и сканирует due schedules между выполнениями; он не создаёт запросы в ChatGPT и не блокирует RSS worker. Точность интервала — **best effort**, а не cron/SLA: пока worker занят длинной операцией, другое Action может быть поставлено в очередь позже.

**История:** хранить успешные и неудачные попытки, источник запуска, версии Action, реально использованные инструменты, `IngestionRun` Feedbrain, дату и наблюдаемые счётчики. Результат может быть ссылкой на данные внешнего приложения.

**Выполнение в V1 (написано, PostgreSQL проверка ожидается):** миграция `20261104_0005` добавляет `ActionRun`, `ActionStepRun` и `ActionResult`. API привязывает новый Run к конкретной неизменяемой версии и проверяет **весь** Workflow и доступность источников до постановки в очередь. Один Action может иметь лишь один активный queued/running Run; параллельная попытка возвращает `409`. Состояния Run: `queued → running → completed/failed`; после сбоя возможен `interrupted`.

Отдельный Docker `action-worker` через PostgreSQL `FOR UPDATE SKIP LOCKED` забирает Run, выполняет шаги Broker последовательно и сохраняет шаг/инструмент **до** внешнего HTTP-вызова. Когда Feedbrain возвращает `202`, worker записывает ссылку на внешний `IngestionRun` **до** его опроса; при завершении сохраняет результат и счётчики. После сбоя запуск, находящийся в `running` больше двух часов, помечается `interrupted`, **без автоматического повторного запроса к Feedbrain**: исход уже посланного задания может быть неизвестен.

### Action Scheduler V1 (код готов; Docker-проверка ожидает обновления)

- Миграция `20261104_0006` создаёт **отдельную изменяемую** таблицу `action_schedules`: `action_id` (уникальный), `enabled`, `every_minutes`, `next_run_at`, `last_enqueued_at`, `last_skipped_at`, `last_skip_reason`. Ни миграция, ни наличие `schedule` в YAML **не включают расписания автоматически**.
- `PUT /actions/{id}/schedule` с `{"enabled":true}` включает расписание; интервал берётся из существующей настройки, а при первом включении — из текущей версии YAML. Можно явно передать `{"enabled":true,"every_minutes":5}`. Время первого срабатывания — **после полного интервала с момента включения**, не немедленно. `{"enabled":false}` выключает будущие постановки в очередь, но не отменяет уже запущенный/queued Run. `GET /actions/{id}/schedule` показывает состояние и следующую дату.
- При каждом срабатывании Scheduler фиксирует **текущую ActionVersion** в новом `ActionRun` с `initiated_by: "schedule"`. Если версия изменена, следующий Run использует новую; уже созданные Runs никогда не меняют свою версию. Изменение YAML `schedule` само по себе не меняет уже активный интервал: им управляет отдельный API.
- Для каждого Action одновременно допускается только один Run в `queued/running`. Scheduler и ручной API синхронизируются блокировкой строки Action; при конфликте Scheduler **пропускает интервал**, пишет `last_skip_reason: active_run`, не создаёт второй Run. Неисполняемый Workflow также пропускается с причиной. При длительном выключении worker пропущенные интервалы **не воспроизводятся пачкой**: один запуск, затем ближайший будущий интервал. Следующее время и запись Run сохраняются в **одной PostgreSQL-транзакции**.
- При включении API проверяет совместимость Workflow с текущими адаптерами (`409` при неисполняемом Action, `422` при неверном интервале). Запущенные автоматически Actions имеют те же результаты, историю, лимиты и правила восстановления, что и ручные.
- Реализация: `src/info_hub/action_schedule_services.py`, `action_schedule_api.py`, `action_schedule_time.py`; тесты расчёта интервалов проходят без БД. SQL/API интеграционные тесты подготовлены, **на настоящей PostgreSQL не выполнялись**. До обновления Docker состояние `schedule_active` на работающем API ещё отражает старую версию кода.

### API для человека и внешнего AI

**Реализованы и проверены на развёрнутом API через Fortis Repo:**

| Метод | Endpoint | Назначение |
|---|---|---|
| `POST` | `/actions` | Создать Action v1 из JSON `{"definition_yaml": "..."}` |
| `GET` | `/actions` | Список Actions (пагинация `offset`/`limit`) |
| `GET` | `/actions/{id}` | Текущая версия, инструкция, нормализованное определение, исходный YAML |
| `POST` | `/actions/{id}/versions` | Создать новую редакцию через `definition_yaml` и обязательный `expected_version` |
| `GET` | `/actions/{id}/versions` | История версий, новые первыми |
| `GET` | `/actions/{id}/versions/{number}` | Точная неизменяемая редакция |

**Особенности реализации:** `Action` содержит стабильный ID и указатель на текущий номер версии; `ActionVersion` хранит **исходный YAML и нормализованный JSONB-снимок**, не содержит внешних ключей к Feedbrain. В миграции `20261104_0004` PostgreSQL-триггер запрещает `UPDATE` и `DELETE` версий. Создание v2 блокирует строку Action и проверяет `expected_version`: при устаревшей редакции API возвращает `409`, при неправильной схеме — `422`, при отсутствующем Action — `404`. **Расписание из YAML остаётся декларацией**. После обновления `schedule_active` отражает фактическое включение расписания **для текущей версии**; исторические версии никогда не исполняются по действующему расписанию.

**Новые маршруты добавлены в код, ждут проверки на Windows Docker:**

| Метод | Endpoint | Операция |
|---|---|---|
| `POST` | `/actions/{id}/runs` | Создаёт queued Run, возвращает `202`; можно указать `{"version_number": 1}`, по умолчанию текущая версия. |
| `GET` | `/actions/{id}/runs` | История запусков с состояниями и точными номерами версий. |
| `GET` | `/action-runs/{run_id}` | Подробный Run, шаги, ссылка на Feedbrain IngestionRun, результат и ошибки. |

**Добавлены в код (пока без Docker-проверки):** `GET /actions/{id}/schedule` и `PUT /actions/{id}/schedule`. Состояние по умолчанию — `enabled: false`. Внешний AI через Fortis Repo уже инициировал и прочитал ручной Run #1; запуск по расписанию ещё предстоит проверить после обновления Docker. Полноценный собственный MCP-сервер не требуется.

**Безопасность:** сейчас Feedbrain API вообще не требует токенов. До предоставления новых mutating endpoints недоверенным клиентам нужна хотя бы локальная защищённая модель доступов, а в проекте — отделение чтения от создания/запуска/изменения Actions. В раннем тесте использовать только доверенную локальную сеть и явный набор разрешённых subscriptions; не давать Broker выполнять произвольные HTTP-команды из Workflow. Детали см. [SECURITY.md](SECURITY.md).

## 5. Один полный end-to-end сценарий

```text
Создать Action «Обнови выбранный RSS-архив»
        │
        ▼
Сохранить инструкцию + Workflow в PostgreSQL
        │
        ▼
Прочитать Action через API (в т. ч. из ChatGPT/Fortis Repo)
        │
        ▼
POST: запустить Action вручную
        │
        ▼
ActionRun queued → worker → Broker
        │
        ▼
information.sync → Feedbrain adapter → POST /subscriptions/{id}/sync
        │
        ▼
Feedbrain IngestionRun → polling GET /runs/{id}
        │
        ▼
ActionRun completed/failed + StepRun + внешняя ссылка/счётчики
        │
        ▼
GET: посмотреть историю Action
        │
        ▼
Включить расписание Action → убедиться в самостоятельном новом Run
        │
        ▼
Создать ActionVersion v2 → проверить, что старые Run связаны с v1
```

**Отдельно проверить:** если Feedbrain недоступен, нет подходящей capability, подписка выключена или RSS возвращает ошибку — ActionRun фиксирует корректный исход и причину. Автоматический запуск должен происходить **без запроса к ChatGPT**, пока работают Docker/worker.

## 6. План работ V1

Эти задачи уточняют **Phase 1** в [PROJECT.md](PROJECT.md); отмечать фактическое выполнение следует **там**, а не в двух файлах.

1. **Контракт YAML:** выбрать минимальные поля; валидировать с отказом от неподдерживаемых операций; определить, что инструкция без Workflow хранится, но не исполняется нашим worker.
2. **Action Registry:** модели, миграция, версии и HTTP API **проверены через Fortis Repo** на работающей PostgreSQL (Action #1 v1→v2, сохранность YAML, ошибки `409`/`422`). Отдельная проверка прямого SQL-триггера и disposable-DB тесты остаются для последующей проверки.
3. **Broker + Feedbrain adapter:** успешный реальный вызов через ActionRun #1 / Feedbrain IngestionRun #6 подтверждён, результат и счётчики сохранены; failures/timeouts покрыты локальными тестами.
4. **ActionRun и история:** новая PostgreSQL-миграция, Action worker, API и успешная история Run #1 / StepRun #1 / ActionResult **проверены**; проверить отдельно реальные ошибки, восстановление после рестарта и автоматические Runs.
5. **Расписание:** модели/миграция `0006`, API включения/отключения, опрос в Action worker и защита от дублирующихся запусков **написаны**. Дождаться проверки двух реальных scheduled Runs на Docker и поведения после рестарта.
6. **End-to-end тест:** ручной и плановый запуск, история, v1/v2, доступ через Fortis Repo, негативные сценарии.

### Definition of Done V1

**Система действительно работает, если** можно создать Action в удобном для AI формате, прочитать его через доступный Fortis Repo HTTP-инструмент, запустить вручную, увидеть **фактическую** команду Feedbrain и завершённый `IngestionRun`, посмотреть историю Action/Step/Result, настроить расписание и убедиться, что worker самостоятельно создал и завершил следующий Run. Всё это подтверждается проверкой на Docker/PostgreSQL, а не только чистыми unit-тестами.

Разделение для проверки: **Phase 1 закрывается только после этой цепочки**. Не утверждать об автоматическом расписании без наблюдения двух разных запланированных запусков и их статусов (как минимум один после заданного интервала).

## 7. Что откладываем и что оставляем открытым

**Не входит в V1:** автоматические вызовы облачной/локальной AI-модели, собственные средства запуска локальных моделей, AI-управляемое планирование шагов, рынок игр/Goal Map как обязательные интеграции, графы/графики, накопительные представления, универсальный MCP-сервер, marketplace инструментов, условия, циклы, параллелизм, nested Actions, cron, собственный workflow DSL с произвольными выражениями.

**Дальше, по реальным задачам:** подключить второй инструмент с той же capability и проверить выбор через `tool` **в новой версии Action**, добавить передачу результатов между шагами, затем инструменты анализа/AI. Альтернативный готовый workflow-движок имеет смысл изучать **только при необходимости**.

**Ещё требуют решения перед следующими шагами:** место хранения конфигурации инструментов/секретов; семантика расписания при изменении версии Action; timeout и обработка уже активного Feedbrain Run; границы разрешений для действий через Fortis Repo. Варианты выше — базовые предложения, не реализованные решения.
