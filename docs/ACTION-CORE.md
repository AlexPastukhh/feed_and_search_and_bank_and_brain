# Action Core — подробный план и проектные решения

> **Статус:** проектирование, **не реализовано**. Обсуждение на 2026-11-04.
> Этот файл раскрывает следующий этап из [PROJECT.md](PROJECT.md) и связанные с ним будущие этапы. Общие границы системы и терминология — в [ARCHITECTURE.md](ARCHITECTURE.md); фактический прогресс, отметки и история — **только** в [PROJECT.md](PROJECT.md).
> Примеры ниже **иллюстративные**, не утверждённая грамматика и не действующее API.

## 1. Суть и граница ответственности

**Action — сохраняемое, преимущественно понятное AI описание того, что нужно сделать.**
Оно может содержать цель на естественном языке, инструкции, ограничения и **необязательное** описание управляемой последовательности действий (Workflow). Структура помогает инфраструктуре запускать, планировать, версионировать и отслеживать работу; она **не должна** заставлять автора задачи заранее расписывать алгоритм, конкретный набор API-вызовов или тип предметной области.

**Action System** отвечает за определения и версии Actions, управляемое выполнение, сопоставление требуемых возможностей с доступными инструментами, историю и расписания. Она **не** обязана хранить все данные, обслуживать все API, реализовывать визуализацию или содержать собственную LLM.

**Инструменты — чёрные ящики.** Сторонние и свои приложения подключаются через реально доступные интерфейсы: API, MCP, CLI, SDK, файловые операции, разрешённую браузерную автоматизацию либо адаптер. Внутренняя реализация инструмента вне скоупа Action Core. Если инструмент не подключён или не поддерживает требуемую операцию, выполнение **не должно выдавать успех**.

**Feedbrain** — необязательный инструмент получения и поиска накопленной информации; его RSS worker может работать по расписанию **без AI**. Goal Map, GitHub, внешние поисковые системы, приложения графов/таблиц, обработчики файлов и локальные модели — равно допустимые поставщики возможностей. Данные могут передаваться напрямую между приложениями, **без обязательного импорта в Feedbrain**.

## 2. Что мы хотим обеспечить

- **Читаемость для AI:** сохранённый Action можно показать ChatGPT/другой модели, попросив «прочитай инструкцию и выполни»; текст сам по себе остаётся осмысленным.
- **Необязательный Workflow:** для повторяемых задач можно описать шаги и зависимости понятным инфраструктуре декларативным способом. Простой Action может состоять только из инструкции.
- **Смешанное исполнение:** обычная программа собирает/фильтрует данные → AI анализирует → другой инструмент сохраняет/визуализирует. AI здесь — **один из инструментов**, а не обязательное исключение.
- **Два направления взаимодействия с AI:** Action может вызывать AI как capability; AI-клиент может сам читать/создавать/запускать Actions и регистрировать результат, если ему предоставлены соответствующие полномочия.
- **Разные исполнители:** выполнение может вести внешняя модель, локальная модель, программный worker или управляемая последовательность из нескольких инструментов. В будущем Action может инициировать запуск локального inference runtime или другого Action.
- **Заменяемость:** Action ссылается на нужные **возможности/контракты**, а не на реализацию. Замена инструмента без изменения Action допустима **только** при совместимости входов, выходов, ограничений и семантики. Для специфичной задачи допускается явная привязка к инструменту/модели.
- **Управление во времени:** история версий, запусков и шагов, явные результаты, ошибки, сохранение ссылок на внешние представления, планирование и потенциально условия повторного запуска.
- **Экономия ресурсов:** извлечение/индексация/фильтрация и другие механические действия выполняются обычными инструментами, когда LLM не нужна. Вызовы AI и тексты, возвращённые модели, всё равно расходуют её контекст/токены.

## 3. Понятийная модель

| Понятие | Ответственность | Нюанс |
|---|---|---|
| `Action` | Стабильная идентичность задачи, имя, текущая редакция | Не означает отдельный вид AI-промпта или предметный модуль |
| `ActionVersion` | Неизменяемый снимок текста, необязательного workflow и остальных настроек | Новые инструкции, источники и критерии → новая версия |
| `Workflow` (необязателен) | Управляемые операции, порядок и ссылки на результаты шагов | **Не** обязательно фиксированный набор «команд» или собственный язык программирования |
| `Capability` | Семантическая операция, которую требует шаг (`information.search`, `representation.update` и т. п.) | Имя без контракта аргументов/результата недостаточно |
| `Tool / Service` | Конкретная реализация одной или нескольких capabilities | Один сервис может реализовать несколько; несколько сервисов — одну |
| `Connection / Adapter` | Способ реально обратиться к инструменту и описать его поддерживаемые операции | MCP/REST/etc. — транспорт/интерфейс, а не отдельная бизнес-логика |
| `Capability Broker` | Сопоставление запроса с **доступным и разрешённым** исполнителем операции | Название предварительное; не обязательно отдельный процесс/продукт |
| `Execution Engine / Orchestrator` | Запуск, управление шагами, передачей результатов и статусами | Не надо путать с самим AI; допускается внешний workflow-движок |
| `ActionRun` | Факт одного запуска определённой версии | Отделён от `IngestionRun` Feedbrain |
| `StepRun / Event` | Что реально делалось, каким инструментом, когда, с каким исходом | История может быть детальнее, чем итоговый Run |
| `ActionResult` | Итог/сводка и ссылки на созданные/обновлённые объекты | Не обязательно копировать стороннюю БД или результат целиком |
| `ActionSchedule / Trigger` | Условие будущего запуска Action | Не путать с периодом RSS polling внутри Feedbrain |
| `ExecutionPolicy` | Машиночитаемые права, лимиты, запреты, подтверждения | Текст Action **не является** источником разрешений |

Названия сущностей, состав таблиц и точные границы компонентов ещё **не утверждены**. При реализации можно использовать существующий backend и PostgreSQL, но логически Action Core должен работать **без Feedbrain** и без обязательных внешних ключей к его `Resource`/`Subscription`.

## 4. Модель Action и варианты исполнения

### 4.1. Свободная инструкция

```yaml
name: Изучение рынка игровых механик
instruction: |
  Исследуй рынок игр за выбранный период.
  Сравни игры с интересующими меня механиками,
  используй доступные источники и покажи
  различия относительно предыдущего периода.
```

Такой Action AI может прочитать и выполнить **самостоятельно**, через уже доступные ему инструменты. Инфраструктура должна уметь выдать конкретную версию и принять сведения о выполнении; наличие Workflow не является обязательным условием существования Action.

### 4.2. Декларативный Workflow (условный синтаксис)

```yaml
name: Мониторинг практических решений
instruction: |
  Поддерживай знания о способах достижения целей
  и требованиях в актуальном состоянии.

workflow:
  - do: information.collect
    with:
      sources: chosen_sources
      since: last_success
    save_as: new_items

  - do: information.filter
    with:
      input: $new_items
      strategy: only_new
    save_as: changes

  - do: reasoning.analyze
    with:
      input: $changes
      question: Найди новые решения и изменения оценок эффективности.
    save_as: proposals

  - do: knowledge.propose
    with:
      target: goal_map
      input: $proposals
```

Это **НЕ** готовая грамматика. `do` обозначает **намерение вызвать capability**, а не хардкод конкретного API. Например, `reasoning.analyze` может выполнять облачная/локальная модель или иной совместимый инструмент. `knowledge.propose` может предоставлять Goal Map. Не нужно немедленно писать реализации таких операций или навязывать именно эти имена.

Данные между шагами могут передаваться **ссылками** на объекты другого сервиса, а не переноситься целиком в наш процесс или в контекст AI. Накопительные графы/таблицы/датасеты обновляет соответствующий инструмент; Action задаёт, **что** обновить и какой результат нужен.

### 4.3. Три маршрута исполнения

```text
A. Пользователь / AI: «прочитай Action и выполни»
   → ActionVersion → внешний AI с разрешёнными инструментами
   → результат + регистрация Run

B. Scheduler / API / другой Action: «запусти Action»
   → ActionRun → Execution Engine → Broker → доступные инструменты
   → события шагов → результат

C. Внутри Workflow: «вызови модель»
   → Broker → облачный или локальный AI tool → ответ/ссылка
   → следующий программный/внешний шаг
```

Варианты могут сочетаться; инициатор запуска и исполнитель — **разные** свойства. Вариант A технически возможен как ручной сценарий через чат, но **автоматический** запуск ChatGPT по времени из нашей БД пока **не реализован**. Вариант C также не означает, что в ядре должна быть встроенная LLM.

### 4.4. Локальные модели и программные операции

Возможность исполнить шаг через локальную модель (вызов inference API, запуск/остановка процесса или сервиса) должна вписываться в **тот же контракт инструмента**. В будущем понадобится адаптер, управляющий доступностью модели, GPU/RAM, тайм-аутами и ресурсами; писать свой LLM runtime не требуется.

С тем же подходом работают программы без AI: обычный fetch, SQL/filter, конвертация, backup, экспорт, создание графика. **Action** полезен для управляемых задач, а не для замены каждого внутреннего вызова API на новый Action.

### 4.5. Action может вызывать другой Action

При наличии соответствующего инструмента и разрешений AI или workflow сможет инициировать другую задачу. Потребуются `parent_run_id`/причинная связь, лимиты глубины и числа вызовов, бюджет, защита от рекурсивных циклов, возможность остановки; это **будущий этап**, не обязательство реализовать рекурсию сейчас.

## 5. Интеграционный контракт и маршрутизация

```text
Action / Workflow: «какая capability нужна»
               │
               ▼
Execution boundary / Broker
    ├─ проверить требуемую семантику и параметры
    ├─ найти доступные совместимые инструменты
    ├─ проверить доступ и разрешённые операции
    ├─ выбрать реализацию (или запросить уточнение)
    ├─ выполнить вызов и проверить результат
    └─ записать факт, версии, время и итог
               │
        ┌──────┴────────┬──────────┐
        ▼               ▼          ▼
   Feedbrain        Goal Map    API/MCP/CLI/
   RSS/архив         знания     AI/локальный runtime
```

**Ключевое требование:** возможность перенаправить операцию на другой инструмент **без переписывания смыслового Action**. Для этого недостаточно общей метки; следует договориться о:
- имени и **значении** операции, допустимых аргументах и формате результата;
- ограничениях по источникам/типам данных, полноте, свежести, стоимости и правам;
- поддержке асинхронных операций, ошибок, повторов и идемпотентности;
- способе привязки результата к следующему шагу (значение или ссылка);
- детерминированности выбора, если доступно несколько инструментов.

При отсутствии совместимого инструмента — явное `capability_unavailable`, а не подмена операции чем-то похожим без согласия. Для AI-управляемого режима AI может предложить альтернативу, но системные permissions не меняются.

**Не нужно делать собственный Broker слишком рано.** Сначала можно применить явное сопоставление 1–2 операций с существующими инструментами и проверить реальную замену адаптера. Собственный registry/оркестратор развивать, только когда необходимость подтверждена.

## 6. Планирование, история и безопасность

### История

- `ActionVersion` не изменяется после публикации; Run закрепляет точную версию.
- При запуске фиксируются **кто инициировал**, **кто исполнял**, фактическое время, входные параметры и статус.
- Для шагов — фактически использованный инструмент, операция и версия/идентификатор инструмента, ссылка на входные данные и результат, время, ошибки и расходы (если доступны).
- `ActionResult` содержит краткий итог и ссылки на внешние документы/представления, provenance и Evidence, если есть. Не копировать приватный контент и токены в логи без необходимости.
- Изменение Action или замена инструмента не переписывает историю предыдущих выполнений. **Повторный запуск не гарантирует битового совпадения результата** при изменяющихся источниках и недетерминированном AI.

### Расписания и события

- Action допускает ручной, API-инициированный, AI-инициированный, другой Action-инициированный, календарный и событийный запуск.
- Человек может описать намерение «запускай ежедневно» в инструкции/Workflow; **реальное расписание** должно иметь однозначную машиночитаемую интерпретацию, тайм-зону, политику пропусков и повтора (через ActionSchedule/Trigger или совместимый внешний scheduler).
- Программа может запускать сбор без LLM, а следующий шаг — обращаться к AI; RSS polling Feedbrain остаётся **отдельной** подпиской и расписанием.
- Scheduler отвечает **когда**, Orchestrator — **что происходит при запуске**, инструмент — **как выполнить конкретную операцию**.

### Безопасность

Текст Action/Workflow может содержать намерение, но **сам себе полномочий не выдаёт**. Контроль доступа — отдельная проверка: субъект, разрешённый инструмент и операция, scope чтения/записи, подтверждение изменений, квоты, тайм-ауты, расходы, аудит. Внешние источники/ответы инструментов считаются недоверенными данными, а не управляющими инструкциями.

Пока Feedbrain API вообще без авторизации. Перед распространением доступа за пределы доверенного локального окружения нужны необходимые ограничения, описанные в [SECURITY.md](SECURITY.md).

## 7. План реализации: от контракта к проверенной системе

**Важное разделение:** следующий этап **Phase 1** — минимальное хранение и управление Actions, но при проектировании учитываем будущие Workflow/Broker/AI/локальные модели. Реальную автоматическую оркестрацию не надо выдавать за часть готового Phase 1. Этапы исполнения синхронизированы с [PROJECT.md](PROJECT.md), где ведутся **единственные чекбоксы прогресса**.

| Шаг | Что проектируем / проверяем | Граница |
|---|---|---|
| **1. Контракт Action (Phase 1)** | AI-читаемая инструкция; необязательный workflow как версионируемое содержимое; неизменяемый снимок; минимальные metadata/policy; интерфейс результата | Пока не выбираем полноценный DSL и не создаём оркестратор |
| **2. Хранение и API (Phase 1)** | `Action`, `ActionVersion`, `ActionRun`, `ActionResult`, миграции, CRUD версий, история и явные переходы Run | Без вызова AI, автоматического выбора инструментов и расписаний |
| **3. Первый внешний исполнитель (Phase 2)** | AI получает сохранённую версию через API/MCP-подобный доступ, выполняет с имеющимися инструментами, возвращает результат и ссылки | Разграничить доступ и честно журналировать фактические вызовы |
| **4. Реальный Action v1→v2 (Phase 3)** | Goal Map: чтение, исследование, предложения; либо рынок игр по параметрам; история двух запусков | Не встраивать доменную логику в Action Core |
| **5. Минимальный Workflow (Phase 2–4, отдельный вертикальный срез)** | 1–2 capability, результаты шагов, явное сопоставление с инструментами, смешанный программный/AI сценарий | Порядок относительно первых ручных Actions уточнить по потребности |
| **6. Broker и переносимость (по мере нужды)** | Контракты и замена одного инструмента другим без изменения Action | Не строить общий marketplace до проверки на двух реализациях |
| **7. Schedules, Events, nested Actions (Phase 4)** | Реальные плановые/событийные запуски; учёт ошибок, разрешений, циклов и затрат | Только после доказанного доступного исполнителя |
| **8. Representations, Feedbrain, local AI (Phase 5–6)** | Накопление во внешних сервисах; дополнительные источники Feedbrain; локальные модели как Tool/Executor | Создавать адаптеры по конкретному Action |

### Критерий готовности ближайшего этапа (Phase 1)

1. Создать Action с понятной человеку/AI инструкцией **без обязательного Workflow**.
2. Сохранить опциональный Workflow (как версионируемое описание; **не обещать его выполнение** на этом этапе).
3. Выпустить v2 с новой инструкцией/Workflow; v1 неизменна.
4. Через API зарегистрировать Run для выбранной версии, завершить его статусом и сохранить результат со ссылкой на внешний объект.
5. Прочитать историю: версия, инициатор/исполнитель, запуск, результат. Нельзя незаметно изменить прошлый Run или его ActionVersion.
6. Проверить тестами и в **изолированной** PostgreSQL; Action Core не требует Feedbrain Source/Resource и не вызывает AI без явной интеграции.

**Отдельный критерий переносимости (не Phase 1):** выполнить один и тот же смысловой Action через две совместимые реализации capability, меняя binding инструмента, **не изменяя ActionVersion**. Без этой проверки независимость остаётся только проектным принципом.

## 8. Вопросы, которые остаются открытыми

1. **Формат Workflow:** нужен ли ограниченный YAML/JSON DSL, существующий стандарт или гибрид с инструкцией для AI? Как проверять версии схемы, ветвления и зависимости без изобретения нового языка программирования?
2. **Граница интерпретации:** что всегда выполняется строго программно, а когда AI может свободно планировать шаги? Как явно различать эти режимы?
3. **Контракты capabilities:** какие минимальные параметры/типы обязательны, как описать поддержку разных источников, streaming и async?
4. **Выбор инструмента:** фиксированная привязка, приоритеты, ручное разрешение или AI-предложение? Как не подменить источники/качество без ведома пользователя?
5. **Модель выполнения:** собственный Orchestrator, внешний готовый workflow-сервис или оба через адаптер? Где находится доступный постоянно работающий executor?
6. **Локальные модели:** кто запускает/останавливает runtime и управляет GPU/RAM; как безопасно ограничивать CPU/GPU/время?
7. **Сохранение истории:** сколько фактических данных хранить локально, а сколько — ссылками на внешние приложения; приватность, retention, стоимость.

Ни один из этих вопросов **не должен блокировать** простое версионируемое хранение Action, но решения об интерпретаторе и маршрутизации нужно принять **до** реализации соответствующих функций, а не выдавать примеры YAML за готовый контракт.

## 9. Ближайшее действие

Согласовать **минимальный контракт Phase 1**, особенно что считается инструкцией, как хранится **необязательный** Workflow и что фиксируется в `ActionRun`. Затем реализовать версии, API и историю. Доказать доступ через существующий внешний AI, прежде чем выбирать собственный язык или писать универсальный Broker.
