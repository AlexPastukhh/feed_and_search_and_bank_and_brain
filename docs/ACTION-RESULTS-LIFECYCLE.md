# Action results: история и сквозные циклы

**Статус:** предметный контракт/план, не утверждение о реализованном API.
Связанные сценарии: [UC-ACT-010/011](use-cases/result-lifecycle.md),
[UC-ACT-009](use-cases/review-results.md),
[UC-ACT-006](use-cases/information.md#uc-act-006).
Технические границы — [ACTION-CORE](ACTION-CORE.md).
Операционные режимы исполнения и ответственность за их жизненный цикл —
[EXECUTION-MODES](EXECUTION-MODES.md); это не значения семантической категории Action.

- Работающий Core сохраняет ActionRun/StepRun/Result для **программного**

- Категории research и monitoring различаются **назначением**, не

## Граница между исполнением, результатом и применением

| Что | Владелец | Что сохраняется |
| --- | --- | --- |
| Action и версии | Registry | Точная инструкция и категория |
| История исполнения | ActionRun (целевое расширение) | Run ID, версия, исполнитель, даты, статус, ошибки, result refs |
| Research | Внешнее разрешённое хранилище | Анализ, Evidence, предложения, report |
| Monitoring | Внешнее разрешённое хранилище и при нужде dataset Tool | Snapshot, типизированные наблюдения, изменения |
| Решения после обсуждения | Отдельный журнал или приложение | Отзыв, approval/rejection, выполненная операция и её readback |
| Графики и таблицы | Отдельный разрешённый Tool | Чтение dataset, выбор метрик, фильтры и визуализация |

Core не обязан хранить предметные JSON, таблицы, графики, полный
ответ AI или приватные данные. Достаточно безопасных ссылок и истории.
Результат не равен выполнению, а предложение не равно применённому
изменению. Не вводить универсальный Artifact Registry.

## Обязательная адресуемая запись выполнения (цель)

Единый минимум для Research, Monitoring и других Actions:

- run_ref / run_id; action_id + неизменяемая action_version;
- режим управления исполнением (External AI, Managed AI или Programmatic —
  **операционные** варианты, не новые значения `action.category`),
  независимо — инициатор и идентичность исполнителя, известные
  started_at/finished_at, статус, ошибка. Конкретное поле/enumeration Core
  ещё не реализовано; `external_ai_manual` в уже сохранённых отчётах —
  локальная метка происхождения, не API-режим;
- input_scope/параметры, реально использованные Tools и источник данных,
  если известны; previous_run_ref при сравнении;
- output_refs (проверенные URI), storage_status (saved/not_saved),
  краткое summary, dataset_ref и schema_version если есть;
- идемпотентная регистрация без подмены уже закрытого исполнения.
  Логи хранят метаданные, не массовые чужие объявления и не секреты.

**Недостающий минимальный технический шаг:** отдельный безопасный
контракт регистрации **факта внешнего выполнения** с фиксацией точной
версии Action, известных дат/исхода и ссылок на реально записанные
результаты. Для текущего ChatGPT через Fortis Repo достаточно
авторизованной идемпотентной регистрации **после выполнения**, без
обязательного старта/heartbeat в Core. Он может
расширить существующий ActionRun, а не создавать параллельный общий
реестр. Такой Run НЕ ставится в очередь программного Broker и не имеет
фиктивных StepRun. Перед реализацией подтвердить полномочия записи,
валидацию состояний и идемпотентность. API регистрации **пока нет**.
Не считать статус выполнения completed доказательством сохранения:
отдельно учитывать storage_status.

**Временная история:** metadata.run_key/report_id внутри отчётов плюс
индексы [Research №3](research/action3/README.md) и
[Monitoring №4](monitoring/action-4/README.md). Позже привязать их
к Core без выдуманных автоматических запусков или времени выполнения.

## Research: сохранение → обсуждение → отдельное решение

**Первая подтверждённая форма хранения (для редких несекретных отчётов):**
приватный Git, путь
docs/research/action<id>/runs/<date>-<run-key>/result.json + report.md.
Индекс связывает run, отчет, версию и предложения. Файл в task-ветке
не равен принятому в main результату; сохранение подтверждается
только после разрешённого PR/merge и независимого чтения.

Цикл: внешний AI самостоятельно читает точную ActionVersion →
AI/Tools → result.json + report.md + Evidence → сохранение и readback →
регистрация факта выполненной работы с output_ref (пока только
метаданные внешнего отчёта, Core API нет) → открытие отчёта в чате →
обсуждение конкретного report_id#proposal_id → **отдельное**
принятие/отклонение/откладывание идеи → по явному разрешению
создать Source через подходящий Tool, создать/версионировать Action
через Registry или ничего не делать → readback фактического изменения.

Сам Research **не создаёт Sources/Actions автоматически**.
Его предметный результат — предложения и понимание. Исторический
отчёт неизменяем. Решение хранить отдельно с полями decision_id,
report_id, proposal_id, решение, who/when, intended_operation,
target_ref, applied_at/verified_at или reason. Предложение со
status=proposed не становится автоматически status=applied.

**Критерий end-to-end:** в новом разговоре можно получить отчёт,
найти предложение по ID, рассмотреть Evidence, принять отдельное
решение и проверить изменение/отказ без редактирования отчёта.

## Monitoring: snapshot → dataset → сравнение/график

**Пилотное хранилище:** docs/monitoring/action-<id>/runs/
<date>-<run-key>/result.json + report.md, плюс индекс. Подходит для
доказательства ручного цикла. Для частого мониторинга Git с PR на
каждый снимок неудобен. Нужен **конкретно выбранный** Tool хранения,
имеющий проверенные write/read/query, права и стабильные dataset IDs.
Feedbrain — возможный Tool только при соответствии реальному API,
не обязательный посредник и не универсальная таблица.

Цикл: ActionVersion + предметная схема → внешний AI/Tool → снимок
наблюдений с Evidence и результатом валидации → сохранение/run_ref →
совместимый предыдущий снимок → дедупликация и классификация
new/changed/unchanged/unknown → накопительный dataset при
необходимости → выборка по фильтру/периоду → таблица или график
через внешний Tool → обсуждение результатов. Изменение Action/Source
остаётся отдельной согласованной операцией.

**Схема задаётся конкретным Monitoring Action/dataset**, не всей
категорией. Минимум для сравнимых записей:

- dataset_id, schema_version, описание колонок, типов, метрик, единиц
  и допустимых null, критерии охвата;
- record_key = стабильный ID предметного объекта (например,
  platform + listing_id), а не локальный FIND-001;
- observed_at и опубликованное source_event_time/published_at
  **раздельно**, source_url/source_id, run_ref, Evidence;
- типизированные метрики/измерения, измеренное или неизвестное
  состояние, proof_level/quality;
- политика дедупликации/истории (append-only snapshots или
  versioned upsert), границы выборки и агрегация для представления.

При необходимости схема экспортируется в CSV/JSONL/таблицу, которую
**реально умеет читать** выбранный аналитический Tool. Первым шагом
достаточно одной проверенной метрики, а не графического движка.

У Action №4 опубликованный бюджет — posted_budget_usd, НЕ заработок;
отсутствие объявления в неполной выдаче НЕ доказательство закрытия.
Два ручных поиска 2026-11-10 — только выборки в один день. Они не
доказывают изменение рынка. Их result.json ещё не является
полноценным историческим dataset, пригодным для трендов.

**Критерий end-to-end:** два сопоставимых запуска дают адресуемые
снимки/наблюдения, корректный diff и читаемые типизированные
данные. Один график/таблица из проверенного Tool должен быть
воспроизводим с исходными полями, датами, единицами и Evidence.
График необязателен для мониторинга, если смысл задачи событийный.

## Минимальный порядок дальнейшей проверки

1. **Выполнено:** PR №6 смержен, новые результаты/индексы
   прочитаны из Docker `main`.
2. Зарегистрировать факт External AI выполнения для Action №3 и №4
   с настоящими ссылками на результаты в общей истории Core
   (после отдельной минимальной доработки API).
3. Research review: разобрать одно предложение, отдельно записать
   решение; при применении проверить настоящий target и версию.
4. Monitoring dataset: выбрать одну схему/показатель, получить
   **сопоставимые** наблюдения и показать данные внешним Tool
   в таблице или графике, не выдавая шум поиска за тренд.

Эти действия не требуют нового типа Action, обязательного Workflow,
нового AI worker, массового коннектора или собственного UI.
