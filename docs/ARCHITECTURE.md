# Архитектура: Action System и Feedbrain

> **Статус:** целевая архитектура, а не описание уже готового продукта. Что действительно реализовано, см. [PROJECT.md](PROJECT.md). Этот документ — единственный актуальный источник архитектурных определений и принципов проекта; прежний Information & Research Platform Draft 0.2 — историческая основа, а не параллельная спецификация.

## Назначение

**Action System** — среда для формулирования, изменения, планирования и отслеживания задач (Actions), которые AI или другой исполнитель выполняет с помощью доступных инструментов. Система связывает **намерение пользователя**, **возможности подключённых приложений**, **исполнение** и **сохранённые результаты**. Способ решения конкретной предметной задачи не должен быть зашит в её ядро.

**Наше первое практическое применение** — поиск, обнаружение и мониторинг информации для принятия решений. В первую очередь ищем реальные оплачиваемые задачи (от .NET/React и любой разработки до 2D/3D и иной работы, которую реально освоить и качественно выполнить с помощью AI/агентов), а также сигналы о новых способах заработка. Другие значимые темы: улучшение собственных AI-workflows, интересующие изменения мира и интернета, новые решения задач из приложения планирования. Эти **предметные сценарии не ограничивают универсальную модель Action**; повторяемые способы использования описаны в [Use Cases](use-cases/README.md).

Примеры Actions:
- Исследовать рынок компьютерных игр за заданный период, с выбранными критериями, жанрами или механиками; сравнить результаты с другим периодом.
- Изучить существующие способы решения технической проблемы и подготовить обзор с первоисточниками.
- Прочитать цели, требования и решения из стороннего приложения (например, Goal Map), найти новые подходы и предложить обновления оценок эффективности.
- Регулярно обновлять накопительные данные и связанные с ними таблицы, графики, графы знаний или отчёты.

**Feedbrain** — уже работающий **подключаемый информационный сервис** для фонового получения, сохранения, подготовки и поиска материалов. Это не Action System, не обязательный посредник для всех данных и не AI-исполнитель. Он может быть одним из инструментов, доступных Action.

## Принцип: приложения — чёрные ящики

**Service/Application** — собственная или сторонняя программа с полезной функцией. Нас интересует её **публичный контракт**, а не её внутренние алгоритмы, база данных, язык реализации или интерфейс пользователя.

- Применяем готовое решение, если оно предоставляет нужные операции с подходящими правами, надёжностью и ограничениями.
- Собственный сервис пишем лишь при конкретном пробеле в функциональности или требованиях.
- Допустимы REST/HTTP API, MCP, SDK, CLI, подключённые файлы, разрешённая браузерная автоматизация и другие машиноисполняемые интерфейсы. **Необходима доступная точка интеграции**, а не обязательный REST API у всех сервисов.
- Если приложение не имеет подходящего интерфейса, может понадобиться адаптер/мост. Подключение не становится автоматическим только из-за существования приложения.
- Для задачи, решаемой напрямую инструментом AI, не создаём обязательный прокси через Feedbrain или нашу БД.

### Контракт операции и граница оркестрации

**Tool — относительно стабильный механизм:** сложный, но насколько возможно предсказуемый способ выполнения операции. Изменяемая стратегия, выбор операций, критерии и параметры задачи преимущественно живут в **Action**; устойчивые алгоритмы поиска, вычислений, дедупликации, ранжирования и обработки могут целиком жить в Tool. Менять Action должно быть существенно проще, чем переписывать Tool. Предсказуемость алгоритма не гарантирует одинакового ответа при изменении данных интернета.

**Инструмент владеет предметным API своей операции:** какие аргументы принимает, какие действия выполняет, что возвращает и как впоследствии прочитать/получить созданные данные. Это могут быть значения, текст, файлы, идентификаторы, ссылки на внешние объекты, сведения об изменениях, инструкции для AI или только подтверждение выполнения. Результат может храниться **у самого инструмента**, не в Action System. Общий обязательный тип результата (файл, артефакт, таблица, универсальная схема `outputs`) **не нужен**.

**Action вызывает доступные операции и оркестрирует их только настолько, насколько требуется задачей.** В декларативном Workflow конкретный инструмент, операция и её аргументы выбираются явно; содержание аргументов и способ получения результатов определяет контракт инструмента/адаптера. Один инструмент может сам обращаться к другому либо предоставить составную операцию, скрывающую несколько внутренних вызовов. **Не нужно искусственно раскладывать её на шаги YAML.** Отдельные шаги нужны, если в них есть смысл; если двум инструментам нужно обменяться данными, предпочтителен предоставленный ими API/прямая интеграция. Action Core **не обязан** переносить файлы, преобразовывать предметные данные или создавать общий канал передачи результатов. Универсальную подстановку ответа предыдущего шага можно рассматривать позднее **только при конкретной неразрешимой существующими API задаче**.

**Общий минимум ядра** — проверка доступности разрешённой операции, запуск, ограничения исполнения и запись истории: какая версия Action, какой шаг/инструмент/операция, статус, ошибка и доступный ответ **или ссылка на него**. История выполнения не равнозначна копии созданных данных. Объёмные/чувствительные ответы и секреты не должны автоматически попадать в БД или контекст AI: достаточно допустимых метаданных и ссылок. Текст/«инструкция для AI», возвращённые инструментом, — **данные**, а не автоматическое разрешение выполнить инструкции; для этого нужен явно выбранный AI-исполнитель с правами и политикой.

### Адаптация к доступным инструментам

Action задаёт **требуемые возможности**, а исполнитель сопоставляет их с
**действительно подключёнными** инструментами: например, один агент получает
данные из API, другой — через MCP, третий — из ранее сохранённого файла.
При отсутствии подходящего инструмента исполнитель должен сообщить о
недоступной capability, запросить подключение/разрешение либо предложить
альтернативу; нельзя молча выдумывать доступ или заявлять, что данные получены.

Можно подключать собственные и сторонние сервисы, а затем заменять их,
не переписывая предметный смысл Action. Это **целевая адаптивность по
контрактам**, а не уже реализованный автоматический marketplace плагинов.

### Термины и границы

| Понятие | Что означает |
|---|---|
| **Service / Application** | Поставщик одной или нескольких возможностей: Feedbrain, Goal Map, сервис графиков, GitHub и т. п. |
| **Connection** | Доступ исполнителя к сервису: endpoint, способ авторизации, настройки; секреты хранятся отдельно. |
| **Capability** | Семантическая возможность: `search`, `read`, `write`, `aggregate`, `render`, `schedule` и т. д. |
| **Tool / Operation** | Конкретная вызываемая операция API/MCP/CLI; сама определяет допустимые аргументы, формат ответа и способы получить результат. |
| **Source (параметр задачи)** | Выбранный Action источник или область поиска — URL, RSS/API, каталог, запрос, набор ресурсов и др.; не обязательная сущность ядра. |
| **Access Method** | Конкретный путь получения информации: API, MCP, веб-поиск, RSS, файл и т. д. |
| **Action** | Долгоживущая постановка задачи: **что** делать, с какой целью и ограничениями. |
| **ActionVersion** | Неизменяемая редакция инструкции и её настроек. |
| **ActionRun** | Одно выполнение определённой версии с зафиксированными параметрами и результатом. |
| **Representation** | Способ организации или предъявления информации — датасет, Markdown, JSON, граф, диаграмма и др. |

**Sources — обычные аргументы операций, которые по умолчанию выбирает Action.** Для нашего поиска/мониторинга они особенно важны, но не имеют привилегированного обязательного места в универсальном Action Core. Если инструмент работает с фиксированным endpoint, подключением или редко меняющимися значениями по умолчанию, это может быть **конфигурация Tool**; Action передаёт конкретный Source, когда его выбор имеет смысл для задачи.

Важно: **Source в текущей модели Feedbrain** — настроенная RSS-точка подключения с `connector_key`. Это локальная модель конкретного сервиса, не глобальная сущность Action System. Операции Feedbrain могут принимать ссылку на такую подписку через параметр Action.

## Логические подсистемы

```text
Пользователь
   │ формулирует/меняет Action
   ▼
Actions + Versions + Policies + Schedules
   │ запрос на исполнение
   ▼
Execution boundary ──► внешний AI (ChatGPT, Claude, Qwen...) / иной исполнитель
   │                        │
   │                        ▼
   │                Разрешённые Tools / Capabilities
   │                        │
   │             ┌──────────┼─────────────┐
   │             ▼          ▼             ▼
   │         Feedbrain   Goal Map     Внешние API, MCP,
   │         архив       цели/решения  web search, файлы,
   │                                 графы, таблицы...
   │                        │
   └───────── результаты / ссылки / события
                            ▼
             ActionRun + History + Result references
```

Это **логические границы**, а не список отдельных микросервисов или обязательных Docker-контейнеров.

1. **Action Definitions:** цель, инструкция и при необходимости конкретные операции, параметры и ограничения; ожидаемые выходы/политики — только там, где они имеют смысл для задачи.
2. **Execution:** передача версии Action исполнителю, отслеживание хода выполнения, остановка, ошибки и результаты. Исполнитель может быть внешним и не обязан работать постоянно внутри нашей системы.
3. **Tool/Capability Access:** обнаружение либо явная конфигурация разрешённых возможностей, адаптеров и подключения. Знание внутренней реализации сервиса не требуется.
4. **Information & Representations:** получение, преобразование, накопление и представление информации силами выбранных приложений.
5. **History & Scheduling:** версии Action, запуски, статусы, ошибки и доступные ответы/ссылки инструментов, расписания и условия запуска.
6. **Security & Policy:** доступ к инструментам, границы операций записи, подтверждение изменений, секреты и аудит.

**Внешний AI**, когда он участвует в исполнении, интерпретирует цель и использует разрешённые инструменты. **Action Workflow V1** явно указывает `tool`, `capability` и необязательные `with` с параметрами **конкретной операции**; `with.source` — пример аргумента Feedbrain, а не обязательное поле любого инструмента. URL подключения и секреты остаются в доверенной конфигурации адаптера. **Action** не содержит программную реализацию функций инструментов. Детерминированный Workflow с фиксированными шагами допустим там, где важны порядок и воспроизводимость, но не требуется для каждого Action.

## Action — не автоматический сбор и не отдельный prompt

Подробности последующих проектных обсуждений и этапы реализации — в
[ACTION-CORE.md](ACTION-CORE.md): контракт **первой версии исполнения с Feedbrain**,
небольшой YAML Workflow, Broker/adapter, ручные и запланированные запуски,
история, доступ из Fortis Repo. Смешанные AI/программные сценарии возможны
позднее, но **не являются частью V1**. Action только с инструкцией для внешнего AI можно сохранить уже сейчас; это ещё не программный запуск. В дальнейшем смешанный Action сможет ожидать действия AI/человека и затем продолжать выполнение, но такой переход состояния пока только целевой. См. [UC-ACT-001](use-cases/actions.md#uc-act-001) и [UC-ACT-007](use-cases/actions.md#uc-act-007). Здесь описаны архитектурные принципы,
а не синтаксис работающего workflow-движка.

Action можно описывать свободным текстом с дополнительными структурированными ограничениями. Ниже — **логическая модель**, часть которой уже реализована в V1 (фактический статус — [PROJECT.md](PROJECT.md)); это **не требование** создавать все перечисленные таблицы:

| Сущность | Ответственность |
|---|---|
| `Action` | Устойчивый ID и назначение задачи |
| `ActionVersion` | Неизменяемый снимок инструкции и, при наличии, Workflow с аргументами операций |
| `ActionSchedule` | Расписание или условие запуска |
| `ActionRun` | Конкретная версия, время, инициатор, статус и ошибка; прочие метаданные — по необходимости |
| `StepRun` / возможные события | Фактические вызовы инструментов, статус, ошибки и внешние ссылки |
| `ActionResult` | Итог запуска и доступные сведения из ответов шагов; внешний результат может остаться у инструмента |
| `ExecutionPolicy` | Разрешённые инструменты/операции, права записи, лимиты и требования к подтверждению |

Редактирование определения Action создаёт новую версию; прошлые Runs сохраняют ссылку на использованную версию. Выбор инструмента/источника и параметры операций могут меняться в новых версиях; **активное расписание — отдельная изменяемая настройка Action, не новая версия**. Следует фиксировать **реально использованные инструменты и внешние версии данных**, а не только разрешённые. Повторный запуск не гарантирует идентичного результата при изменяющихся источниках или недетерминированном AI. `ActionRun` и `IngestionRun` Feedbrain — **разные** сущности: первое фиксирует выполнение задачи, второе — получение данных конкретной подписки.

### Примеры без привязки к реализации инструментов

**Исследование рынка игр:** Action задаёт период, параметры отбора, жанры
или особенности механик и ожидаемый отчёт. Исполнитель выбирает разрешённые
API/MCP/веб-инструменты, использует существующие исторические наборы данных,
при необходимости дополняет их поиском и обновляет таблицы/графики во внешнем
приложении. Для изменения периода или критериев создаётся новая версия Action.

**Поддержание актуальности Goal Map:** Action читает через API стороннего
приложения цели, требования, решения и критерии их эффективности; ищет
новые сведения через доступные инструменты; сопоставляет результаты,
создаёт предложения и, если разрешено policy/подтверждением, обновляет
данные **в самом Goal Map**. Action System не воспроизводит его доменную
логику и не обязана копировать базу целей в Feedbrain. Повторные запуски
могут поддерживать практическую базу знаний в актуальном состоянии.

**Action Schedule** («раз в неделю анализируй изменения и обнови отчёт») и **Feedbrain Subscription** («каждый час синхронизируй RSS») — разные понятия. Второе работает обычным worker без LLM; первое требует доступного исполнителя и механизма запуска. Сохранение инструкции само по себе **не запускает ChatGPT по расписанию**.

## Информация и представления

**Персональный фид, таблицы, графики, отчёты и другие представления предоставляются готовыми приложениями/Tools**, а не собственным UI или обязательной базой Action Core. Actions задают, что искать, как отбирать и куда направлять результат; выбранный инструмент отвечает за публикацию и чтение. AI должен иметь доступ к результатам и запуску разрешённых Actions через реально доступный интерфейс, но это не требует встроенного автоматического AI executor.

Данные могут поступать напрямую в AI либо через промежуточные сервисы. **Обязательного центрального хранилища и обязательного импорта в Feedbrain нет.**

```text
API / MCP / web / RSS / файлы / база
                │
          выбранный инструмент
                │
        данные или ссылки на них
                │
   нормализация / анализ / объединение
                │
   ┌────────────┼────────────┬──────────────┐
   ▼            ▼            ▼              ▼
 Markdown     JSON         Таблица       Knowledge graph
                              │              │
                              ▼              ▼
                        Временной ряд     Визуализация
                              │
                              ▼
                            График
```

**Representation** описывает смысловую форму информации. **Artifact** — конкретно сохранённый файл/экспорт, если он есть. **Resource**, **Observation**, **Entity** — предметные типы соответствующих сервисов. Это **не обязательные типы ответов Action**: их может полностью определять внешний инструмент. Дублировать его таблицы или вводить универсальный реестр представлений без реальной задачи не нужно.

Представления могут быть **накопительными**: добавлять измерения, обновлять существующий датасет, пересчитывать графики или пополнять граф связей. Способ обновления (`append` / `merge` / `replace` / `recompute`) реализует соответствующий сервис/инструмент, а Action задаёт целевое состояние и политику обновления.

Промежуточные данные не обязаны попадать в контекст LLM: детерминированное получение, фильтрация, индексация и агрегация могут выполняться вне AI. **Но все фрагменты, реально переданные модели, всё равно занимают контекст и могут расходовать токены.** Поэтому возвращаем из инструментов ограниченные релевантные результаты со ссылками, а не весь массив.

Для исследований сохраняем происхождение данных и, где возможно, **Evidence**: ссылка на источник, версию, фрагмент, показатель и дату. Отделяем факт источника, опубликованную оценку, пользовательское мнение и вывод AI.

## Почему Feedbrain остаётся полезен

Feedbrain — **опциональный Information Acquisition / Storage / Processing / Retrieval Service**:

- **Source** — настроенный RSS/Atom feed; **Subscription** — периодичность получения и независимые флаги использования `read_enabled`/`research_enabled` (это **назначение**, не права доступа).
- Фоновый worker опрашивает источники по расписанию и сохраняет новые публикации **без участия LLM**.
- Дедупликация и `ResourceVersion` позволяют сохранять историю, а `ContentChunk` + PostgreSQL FTS — находить релевантные фрагменты.
- Публичный HTML можно извлечь **по отдельному запросу**, а не автоматически для каждой RSS-публикации.
- AI через Fortis Repo может читать Feedbrain API. Внешний веб-поиск/API/MCP дополняют архив, если данных не хватает; порядок вызова определяет Action/исполнитель.

Смысл Feedbrain — заранее аккумулировать выбранные источники, разгрузить AI от механических операций, обеспечить историю и повторное использование несколькими исполнителями. Это **не универсальный веб-поиск**, **не единственная точка получения данных** и **не место для реализации Action logic**. Специализированные поисковые API стоит подключать туда, когда нужно накопление/индексация/кэширование; иначе AI может использовать их напрямую.

Детали уже работающего кода и ограничения: [PROJECT.md](PROJECT.md), [RSS-FIRST-SLICE.md](RSS-FIRST-SLICE.md), [CONTENT-SEARCH.md](CONTENT-SEARCH.md).

## Реализация и границы

**Фактическая реализация, проверенные запуски и невыполненные этапы** описаны только в [PROJECT.md](PROJECT.md). Архитектура не требует отдельного универсального реестра представлений, собственного MCP-сервера или встроенной LLM до появления конкретных задач; не создавать пустые модули под целевую схему заранее.

Старый Draft 0.2 описывал преимущественно information/research backend с `ResearchRun`, `Evidence`, `Entity`, `Observation`, `Artifact` и встроенным LLM gateway. Эти понятия остаются возможными расширениями **при наличии задач**, но исследование теперь рассматривается как **частный случай Action**, а встроенный AI — как **опция**, не обязательная ступень.

Для самого Feedbrain остаются правила: коннектор адаптирует внешние данные и не пишет в хранилище напрямую; сервис ingestion отвечает за сохранение; content processing не зависит от RSS; новые форматы/API добавляем по конкретной потребности. Не вводим Kafka, Kubernetes, микросервисы или pgvector без доказанной необходимости.

## Безопасность и ответственность

Чёрный ящик — не означает безусловное доверие. При подключении нужны понятный контракт, авторизация, ограничения, условия использования, ошибки и проверка результата. Внешний контент недоверенный и не может отдавать AI управляющие инструкции. Операции записи и изменения внешних приложений должны иметь scope и при необходимости подтверждение пользователя.

**Текущее состояние безопасности Feedbrain и план разграничения прав** описаны в [SECURITY.md](SECURITY.md). Состояние реализации и ближайшие проверяемые шаги — в [PROJECT.md](PROJECT.md).
