# Режимы исполнения Action — операционная классификация

**Назначение:** уточнение [архитектуры Action System](ARCHITECTURE.md)
о том, **кто управляет жизненным циклом выполнения**. Термины описывают
целевую модель; это **не значения YAML Action**. В исходниках `main`
(после PR №8) у Run уже есть `execution_kind` (`external_ai` / `programmatic`),
но новый маршрут ещё не установлен на Windows Docker. `Managed AI` —
только целевой режим, не допустимый тип нынешней модели.
Практический учёт результата описан в
[ACTION-RESULTS-LIFECYCLE](ACTION-RESULTS-LIFECYCLE.md);
сценарии — в [Use Cases](use-cases/actions.md).

## Две независимые оси

- **`action.category` — семантическое назначение** (`research`,
  `monitoring`, `general`, впоследствии другие). Не определяет
  исполнителя, запуск, набор Tools, формат результатов или расписание.
  Поле уже существует в неизменяемой ActionVersion.
- **Режим выполнения — операционная классификация**: кто инициирует
  работу, кто отвечает за её ход, остановку, сбои и подтверждение
  завершения. Этот режим влияет на требования к API, правам, истории
  и восстановлению. Его логическое место — **конкретный Run**, поскольку
  один ActionVersion может исполняться разными способами. Исходный
  контракт V1 содержит `ActionRun.execution_kind` со значениями
  `external_ai` и `programmatic`; это **не** утверждение о Windows
  runtime или готовности управляемого AI.

Не смешивать способ инициирования (`user`, `api`, `scheduler`, `ai`),
использованные Tools и режим управления жизненным циклом.
Для External AI **не требуется идентификатор исполнителя**:
`initiated_by` обозначает роль инициатора, а не конкретного AI или человека.
Право на запись проверяется отдельно для Action, без записи имени в Run.

## Операционные режимы

| Режим (целевой термин) | Владелец жизненного цикла | Требуемое поведение | Фактический статус |
| --- | --- | --- | --- |
| **External AI** | AI вне Action Core | Сам получает разрешённую ActionVersion и контекст, выбирает Tools, выполняет работу и передаёт итог/ссылки. Core **не запускает** и не останавливает AI; может лишь принять авторизованную запись о состоявшемся выполнении. | ChatGPT через Fortis Repo реально выполнял №3/№4, но Core Run не записан |
| **Managed AI** | Action System либо её управляемый исполнитель | Система инициирует/назначает AI-выполнение и отвечает за состояние, ожидание, таймаут, отмену/повтор и ошибки. Нужна отдельная проверенная интеграция с AI-исполнителем. | Целевой вариант; не реализован |
| **Programmatic** | Worker/Broker/иной программный исполнитель под управлением системы | Core ставит Run в очередь и отслеживает исполнение декларативного Workflow через разрешённые операции Tools, StepRun и ошибки. | Существующий Action Core V1; проверен Broker/Feedbrain |

**Граница классификации — управление выполнением, а не участие LLM.**
Внешний AI может использовать много программных Tools и останется
External AI. Программный Workflow может вызвать AI как одну из
разрешённых возможностей и всё равно оставаться Programmatic, пока
жизненным циклом Run управляет Worker/Broker. Если управляемый AI
вызывает Tools, это Managed AI, а не Programmatic по одному наличию
вызовов. Смешанные и передающие управление сценарии потребуют
отдельно определённых границ ответственности, а не нового
семантического значения `action.category`.

## Текущая цепочка External AI

```text
Пользователь / внешний AI
        │
        ▼
AI (сейчас ChatGPT) ──► разрешённый доступ (сейчас Fortis Repo)
        │                            │
        └── читает ActionVersion ◄───┘
        │
        ├── выполняет инструкцию самостоятельно
        ├── использует разрешённые Tools, если нужны
        ├── сохраняет и проверяет предметный результат
        └── может зарегистрировать факт выполнения в истории
            (source API есть, Windows API пока не обновлён)
```

**Fortis Repo — средство доступа, не обязательный Executor**.
Action не будит AI и не инициирует текущий чат. В будущем другой
авторизованный AI сможет использовать тот же Registry и иной
доступный ему интерфейс без изменения смысла Action.

Внешнему исполнителю **не обязательно** открывать Core Run до начала:
для первого минимального сценария достаточно идемпотентной,
разрешённой регистрации **после выполнения**, с точной версией
Action, известными датами и проверенными ссылками на результат.
Не выдумывать `started_at`, если он неизвестен,
не отмечать непроверенные файлы как `saved` и не создавать фиктивные
StepRun/queued Worker. Регистрация — учёт, **не команда запустить AI**.
Дополнительные состояния running/heartbeat нужны только при
доказанном требовании к контролю длительных внешних исполнений.

## Инварианты и ограничения

1. **Одинаковая предметная задача** допускает любой разрешённый
   режим выполнения; категория research/monitoring не требует
   собственного движка или специализированного исполнителя.
2. **Общая история** может связывать ActionVersion, роль инициатора,
   режим исполнения, исход и output_refs **без executor_id**, сохраняя различие
   между выполнением и сохранением результата. Core не обязан
   копировать отчёты, таблицы и наборы мониторинговых данных.
3. **Права отдельно от типа**: другой AI не получает автоматического
   доступа к приватному Registry, Tools или записи результатов.
   Авторизация записи по Action и защита от ложной регистрации обязательны
   до открытия API недоверенным клиентам.
4. **Статус V1 не преувеличивать**: существующий POST
   /actions/{id}/runs — очередь программного Workflow, а не
   публичная регистрация внешнего AI. Managed AI не работает;
   код post-hoc External AI Run API уже смержен через PR №8;
   отказ от `executor_id` — следующий отдельный source change с
   миграцией `0008`. Он не развёрнут
   на работающем Windows Core и ещё не проверен на отчётах №3/№4.
5. **Ни регистрация, ни результат исследования** не являются
   разрешением создать Source/Action, запустить другой Action,
   обновить мониторинговый dataset или изменить внешнее приложение.
   Это отдельные действия с правами и подтверждением.

**Дальнейшая реализация:** сначала нужен минимальный контракт
регистрации External AI исполнения и readback в общей истории.
Будущий Managed AI и смешанные сценарии вводить при практической
потребности. Решения и незавершённые задачи находятся в
[backlog](BACKLOG-IMPROVEMENTS.md), подтверждённый runtime —
в [PROJECT](PROJECT.md), текущие API и таблицы — в
[ACTION-CORE](ACTION-CORE.md). Здесь не задаются имена методов,
новые таблицы или обязательный закрытый enum.
