# Сквозные сценарии результата и истории выполнения

Общий контракт: [ACTION-RESULTS-LIFECYCLE](../ACTION-RESULTS-LIFECYCLE.md),
операционные режимы управления исполнением —
[EXECUTION-MODES](../EXECUTION-MODES.md); общий маршрут post-hoc
учёта External AI — [UC-ACT-012](external-run.md).
Research и Monitoring **не выбирают тип исполнителя**. Оба допускают
внешний AI по инструкции, программные Tools или смешанный маршрут.

## UC-ACT-010

**Сценарий: исследование → сохранение → обсуждение → действие**

**Когда:** нужно выполнить Research Action и потом использовать его
аналитические выводы или предложения, а не только показать ответ в чате.

**Цель:** каждый запуск имеет точную ActionVersion, доступный
сохранённый результат и историю выполнения; изменения Sources,
Actions и других объектов идут **отдельными решениями**.

**Предпосылки:** Action с объявленным результатом, разрешённое
хранилище с чтением/записью, доступ к проверяемым первоисточникам.
Исполнитель может быть внешним AI без Tools. Код регистрации
смержен в PR №8, но Windows API ещё не обновлён.

**Как:**
1. Прочитать точную версию Research Action и контракт ожидаемых выходов.
   Зафиксировать вопрос, источники и известные даты в metadata.
   В режиме External AI инициатор/AI действует сам, а не получает
   команду запуска от Core; целевая регистрация в Core допустима
   **после исполнения**, без фиктивного состояния `running`.
2. Выполнить исследование разрешённым AI и/или Tools. Отделить факты,
   Evidence, гипотезы, неизвестное. Собрать результат по контракту
   конкретного Action, включая ID предлагаемых изменений.
3. Сохранить result.json и report.md через реальный разрешённый
   инструмент, проверить readback; сохранить доступный report_id,
   run_ref, ActionVersion, известную дату, status и output_refs
   в доступной внешней истории (в Core — после установки нового API).
   До merge PR данные в Git main не считаются доступными.
4. Открыть отчёт в следующем разговоре по report_id, выбрать
   proposal_id, проверить Evidence и обсудить альтернативы.
   **Исследование само не изменяет Sources/Actions**.
5. Записать отдельное решение: approved/rejected/deferred.
   Для approved проверить права и актуальный target; вызвать
   действительный API создания/изменения и выполнить readback.
   Для отказа сохранить причину. Исторический result.json не менять.

**Готово:** можно пройти от версии и факта выполнения до адресуемого
отчёта, выбрать одно предложение, увидеть отдельный след решения
и подтверждённого изменения либо мотивированного отказа.

**STOP/UNKNOWN:** нет разрешённой записи/чтения, примеры слабо
проверены, целевая версия изменилась, approval отсутствует.
Не создавать программный ActionRun для внешнего AI через endpoint,
который принимает только Workflow; не выдумывать факты применения.

**Фактический статус:** исследование выполнено вручную, отчёт опубликован
через PR №6 и прочитан из Docker `main`. Код регистрации Run смержен
(PR №8) и испытан на одноразовой PostgreSQL, но Windows API ещё старый;
отдельный след решения также не проверен end-to-end.

**Связанные UC:** [001](actions.md#uc-act-001),
[004](information.md#uc-act-004), [009](review-results.md).

## UC-ACT-011

**Сценарий: мониторинг → накопление данных → сравнение/график**

**Когда:** нужно наблюдать определённый объект, сигналы, события или
метрики, повторно читать результаты и сравнивать периоды, включая
сценарии таблиц, графиков и дальнейшего обсуждения.

**Цель:** получить типизированные, сопоставимые наблюдения,
связанные с точной версией Action и историей выполнения, а не только
отдельные ответы или несравнимые подборки.

**Предпосылки:** Monitoring Action задаёт предмет и критерии отбора;
определены источники, допустимые права, предметная схема результатов
(или честно указана невозможность сравнения). Есть разрешённое место
сохранения snapshot; для графиков — реально доступный dataset Tool.

**Как:**
1. Прочитать точную ActionVersion, договориться о dataset_id,
   schema_version, ключе объекта, полях и периоде. При External AI
   исполнитель действует самостоятельно; позже он регистрирует
   факт выполнения. При Programmatic Core запускает Workflow Run.
   Managed AI остаётся будущим режимом. Фиксировать отдельно
   инициатора, исполнителя и фактические параметры.
2. Наблюдать через AI и/или Tools; для каждого объекта сохранять
   стабильный record_key, source/URL, observed_at, event_time если
   известно, типизированные значения, Evidence, качество и unknown.
   Не выдавать опубликованный бюджет за доход и поисковый snippet
   за проверенную открытую вакансию.
3. Сохранить result snapshot и прочитать обратно. Указать
   run_ref, предыдущий совместимый запуск и output_refs; история
   Core для внешнего AI требует установки принятого API.
4. При повторе с согласованной схемой сравнить record_key и факты:
   new/changed/unchanged/unknown. Не считать отсутствие в неполном
   поиске удалением. Изменённый фильтр или охват помечать
   несравнимым; у первого Run — baseline_only.
5. Если нужны накопление/графики, отправить нормализованные записи
   в **выбранный** Tool, который действительно умеет write/read/query;
   выбрать метрику и агрегацию; вывести таблицу или график и
   проверить значения, единицы, временные границы и Evidence.
6. Обсудить с пользователем наблюдения, качество, полезность и
   корректировки Action; любые новые Actions/Sources, изменённые
   фильтры и внешние действия выполнять только по отдельному
   разрешённому сценарию, с новым ActionVersion при её изменении.

**Готово:** хотя бы два реально сопоставимых snapshot, проверяемый
diff, доступные типизированные данные в разрешённом хранилище;
если запрошена визуализация — реальный внешний Tool читает их и
показывает воспроизводимый результат. Первым запуском достаточно
baseline, но он не доказывает динамику.

**STOP/UNKNOWN:** неизвестна схема/единица, нет источника данных,
неразрешённый доступ к платформе, повторные поиски с разными
фильтрами, отсутствует Tool или право на публикацию. Без возможности
построить график можно выполнить мониторинг как событие/текстовое
наблюдение; категория не требует таблиц или расписания.

**Фактический статус:** для Action №4 есть два ручных JSON+Markdown
снимка и частичное сравнение. Они не образуют проверенного временного ряда, не загружены в
накопительный dataset Tool и не представлены графиком. Core не
зарегистрировал эти ручные Run; исходный API уже смержен, но в Windows
не развёрнут.
